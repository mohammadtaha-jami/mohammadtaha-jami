T v1 EAM PROJECTS MANAGEMENT

Project: Team Projects Management — an internal Baltazar Team business tool for catalog management, customer records, order capture, and automated Persian RTL PDF invoicing in four formats.

پروژه: Team Projects Management — یک ابزار داخلی تیم بالتازار برای مدیریت کاتالوگ خدمات، ثبت مشتریان، ثبت سفارش و صدور خودکار فاکتور PDF فارسی (راست‌به‌چپ) در چهار قالب مختلف.

Live Reference نسخه زنده teamprojectsmanagement.onrender.com
VERSION v1.0 STATUS Production (deployed) OWNER Team Baltazar STACK Flask · JSON Choose a chapter from the tabs → یک فصل از تب‌ها انتخاب کنید

Team Projects Management is an internal, single-tenant business-operations tool built for Team Baltazar to manage a service catalog (categories, services, and bundled plans), maintain a customer registry, capture sales orders, and automatically generate Persian (Farsi), right-to-left (RTL) PDF invoices in four distinct formats. The system is a Python/Flask monolith with a flat-file JSON persistence layer (no relational database), a server-rendered Jinja2 + Tailwind front end, and a dual-engine PDF pipeline combining ReportLab and Playwright/Chromium, with full Persian typography via arabic-reshaper, python-bidi, and the custom Dana font family.

Team Projects Management یک ابزار داخلی و تک‌مستأجری برای تیم بالتازار است که کاتالوگ خدمات (دسته‌بندی‌ها، خدمات و پلن‌های ترکیبی) را مدیریت می‌کند، دفتر مشتریان را نگهداری می‌کند، سفارش‌های فروش را ثبت می‌کند و به‌صورت خودکار فاکتورهای PDF فارسی و راست‌به‌چپ (RTL) را در چهار قالب متفاوت تولید می‌کند. این سیستم یک مونولیت Python/Flask با لایه ماندگاری فایل‌محور JSON (بدون پایگاه‌داده رابطه‌ای)، رابط کاربری Jinja2 + Tailwind رندرشده سمت سرور، و یک پایپ‌لاین PDF دو‌موتوره ترکیبی از ReportLab و Playwright/Chromium است که تایپوگرافی کامل فارسی را از طریق arabic-reshaper، python-bidi و فونت اختصاصی دانا پشتیبانی می‌کند.

Technical Objectives

اهداف فنی

  1. T1Provide full CRUD management of categories (parent/child hierarchy), services, plans, and customers without requiring a database server.ارائه مدیریت کامل CRUD برای دسته‌بندی‌ها (سلسله‌مراتب والد/فرزند)، خدمات، پلن‌ها و مشتریان بدون نیاز به سرور پایگاه‌داده.
  2. T2Support two order pathways: catalog-based standard orders and freeform custom orders (roadmap / simple / tiered-panel).پشتیبانی از دو مسیر سفارش: سفارش استاندارد کاتالوگ‌محور و سفارش سفارشی آزاد (نقشه‌راه / ساده / پنل سطح‌بندی‌شده).
  3. T3Generate legally presentable, Persian RTL PDF invoices in four distinct visual formats from a single order record.تولید فاکتورهای PDF فارسی و RTL قابل ارائه قانونی در چهار قالب بصری متفاوت از یک رکورد سفارش.
  4. T4Keep the operational footprint minimal: a single container image, no external DB, no message broker, no background worker infrastructure.حداقل نگه‌داشتن ردپای عملیاتی: یک ایمیج کانتینر، بدون DB خارجی، بدون message broker و بدون زیرساخت worker پس‌زمینه.
  5. T5Preserve full audit trail of orders and generated receipts on the container's persistent filesystem.حفظ ردیابی کامل سفارش‌ها و رسیدهای صادرشده روی فایل‌سیستم پایدار کانتینر.

Non-Goals / Explicit Scope Boundaries

خارج از محدوده / مرزهای صریح دامنه

No multi-tenant support (single organization, no auth layer in the current implementation); no relational database, ORM, or query engine; no payment gateway integration (issues invoices, not payment collection); no user account system / login flow.

بدون پشتیبانی چند‌مستأجری (تک‌سازمانی، بدون لایه احراز هویت در پیاده‌سازی فعلی)؛ بدون پایگاه‌داده رابطه‌ای، ORM یا موتور کوئری؛ بدون یکپارچگی درگاه پرداخت (صدور فاکتور، نه دریافت وجه)؛ بدون سیستم حساب کاربری / فرآیند ورود.

Architectural Style — Layered Modular Monolith

سبک معماری — مونولیت ماژولار لایه‌ای

There is no models/ or services/ package split at the filesystem level — the application deliberately keeps everything in four top-level modules (app.py, json_store.py, receipt_pdf.py, seed.py) rather than a package hierarchy, which is appropriate for its scale but called out as a scaling constraint below.

در سطح فایل‌سیستم بسته‌بندی جداگانه‌ای برای models/ یا services/ وجود ندارد — اپلیکیشن به‌عمد همه چیز را در چهار ماژول سطح بالا (app.py، json_store.py، receipt_pdf.py، seed.py) نگه می‌دارد که برای مقیاس فعلی مناسب است اما به‌عنوان یک محدودیت مقیاس‌پذیری در ادامه ذکر شده است.

There is no relational database engine. Each entity is stored as a JSON array of objects in its own file under Database/, accessed exclusively through json_store.py. Every record uses a UUIDv4 string as its primary key (id).

هیچ موتور پایگاه‌داده رابطه‌ای وجود ندارد. هر موجودیت به‌صورت آرایه JSON از اشیاء در فایل مخصوص خود زیر Database/ ذخیره شده و فقط از طریق json_store.py در دسترس است. هر رکورد از یک رشته UUIDv4 به‌عنوان کلید اصلی (id) استفاده می‌کند.

Design rationale — denormalization by intent: both orders and custom-order embed a full customer snapshot (name, phone, address) and, for standard orders, a service/plan detail snapshot at creation time. Invoices must remain historically accurate even if a customer's contact details or a service's price/terms change later in the admin panel.

منطق طراحی — دنرمال‌سازی عمدی: هر دو orders و custom-order یک اسنپ‌شات کامل از مشتری (نام، تلفن، آدرس) و برای سفارش‌های استاندارد، اسنپ‌شات جزئیات خدمت/پلن را در زمان ایجاد جاسازی می‌کنند. فاکتورها باید حتی در صورت تغییر بعدی اطلاعات تماس مشتری یا قیمت/شرایط خدمت در پنل مدیریت، از نظر تاریخی دقیق باقی بمانند.

Build & Run — Local Docker

ساخت و اجرا — Docker محلی

docker build -t team-projects-management:latest .

docker run -d --name tpm -p 5000:5000 \
  -v $(pwd)/Database:/app/Database \
  -v $(pwd)/reciept:/app/reciept \
  team-projects-management:latest

Without the volume mounts above, both the JSON "database" and every generated invoice PDF live only in the container's writable layer and are lost on container recreation.

بدون mount کردن volume‌های بالا، هم پایگاه‌داده JSON و هم هر PDF فاکتور فقط در لایه نوشتنی کانتینر باقی می‌مانند و با بازسازی کانتینر از بین می‌روند.

The live instance (teamprojectsmanagement.onrender.com) is deployed on Render. Render's ephemeral filesystem means Database/ and reciept/ must be backed by a Render persistent disk, or catalog data and invoices are lost on every redeploy.

نسخه زنده (teamprojectsmanagement.onrender.com) روی Render مستقر شده است. فایل‌سیستم موقتی Render یعنی Database/ و reciept/ باید به یک دیسک پایدار Render متصل شوند، در غیر این صورت داده کاتالوگ و فاکتورها با هر ری‌دیپلوی از بین می‌روند.

Backup & Data Durability

پشتیبان‌گیری و پایداری داده

  • Schedule periodic snapshotting of the Database/ directory (nightly tar + off-host copy, or disk snapshots).
  • Treat reciept/*.pdf as an audit trail — retain per applicable invoicing regulations.
  • زمان‌بندی اسنپ‌شات دوره‌ای از پوشه Database/ (tar شبانه + کپی خارج از سرور، یا اسنپ‌شات دیسک).
  • با reciept/*.pdf به‌عنوان ردیابی ممیزی رفتار کنید — طبق مقررات صدورفاکتور نگهداری کنید.

Authentication & Authorization Posture

وضعیت احراز هویت و مجوز

As implemented, the application has no authentication or authorization layer. Both / and /modir — including every mutating POST endpoint — are reachable by any client with network access to the deployed URL. This is an accurate, load-bearing statement about the current codebase, not a hypothetical risk.

در پیاده‌سازی فعلی، اپلیکیشن هیچ لایه احراز هویت یا مجوزی ندارد. هم / و هم /modir — از جمله همه اندپوینت‌های POST تغییردهنده — برای هر کلاینتی با دسترسی شبکه به URL مستقر قابل دسترسی هستند. این یک بیان دقیق و واقعی درباره کدبیس فعلی است، نه یک ریسک فرضی.
